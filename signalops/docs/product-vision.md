# 產品願景：從程式交易走向 BI 系統

## 為什麼做 SignalOps

這個 side project 的出發點不是再寫一個下單程式，而是受到 ESBI 四象限啟發，思考如何讓程式交易從「本人持續操作與維護才會運作」，逐步成為能被量測、委派、稽核與改善的系統。

這裡把 ESBI 當成產品思考框架，不把它當成投資報酬保證：

| 方向 | SignalOps 對應問題 | 目前功能 |
| --- | --- | --- |
| E／S：個人執行 | 我現在必須親自查看哪些訊號與服務？ | 事件時間軸、目前持倉、即時通知 |
| B：系統化營運 | 系統能否在我不盯盤時留下可追蹤事實並自行恢復？ | 事件契約、outbox、worker、runbook、監控 |
| BI：決策支援 | 哪些策略最活躍、曝險如何、資料是否足以支撐決策？ | 營運 KPI、月趨勢、轉換矩陣、資料品質門檻、AI 工具 |
| I：資本配置 | 風險調整後的報酬是否值得配置資金？ | 尚未開放；需先補可靠 fill、成本與資金曲線 |

## 目前能回答的商業問題

- 有多少策略正處於方向性持倉？
- 策略的事件量是否上升，是否出現異常高頻反轉？
- 哪些策略長期沒有新事件，可能需要維護？
- 系統收集的資料能否支撐績效分析？缺口在哪裡？
- broker 或事件平台故障時，資料是否仍可追溯與恢復？

## 下一階段功能門檻

### 可以優先加入

1. 策略健康分數：資料新鮮度、錯誤率、訊號頻率偏離與 worker lag。
2. 通知政策：異常而非每筆事件都通知，並保留確認與處理紀錄。
3. 成本追蹤：雲端、LLM、broker data 與維運時間的單位成本。
4. 多環境與租戶邊界：demo、paper、live 明確隔離，權限採最小化。

### 資料補齊後再加入

1. Fill event：成交時間、價格、數量、手續費與滑價。
2. Equity snapshot：策略與帳戶資金曲線。
3. 風險指標：最大回撤、曝險金額、相關性與情境壓力測試。
4. 資本配置建議：必須顯示假設、限制與人工核准，不自動下單。

## 產品原則

- 先證明資料可信，再增加漂亮 KPI。
- 先支援人的決策，再談自動化決策。
- AI 只能讀取可稽核工具輸出，不以聊天內容取代事實表。
- 任何自動化都必須有失敗模型、觀測方式與回復步驟。
