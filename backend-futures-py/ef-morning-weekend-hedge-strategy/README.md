# 永豐 2 Clamp：22:00 進場截止、冷卻 15 分鐘、01:00 清倉

未來回撤達門檻後固定 `U+1` 的進出場規格見 [Again 與 Clamp 回撤後加一口的進出場 SOP](../EF_DRAWDOWN_UNIT_SOP.md)；目前尚未啟用。

CFCTX15m（財神列車15號）屬於 E 投組，與其餘 12 組策略一同追蹤。舊有 12 組 JSON 升級時保留原部位，新增 CFCTX15m 的追蹤部位為 0，僅處理啟動後的新訊號。

版本：`json-positions-v12-no-h3-cutoff22-cooldown15-short-exit-long`（狀態 schema 12）。本版移除 H3 進場過濾，沿用其餘 Clamp 進出場規則。更新時保留既有 `positions`、待確認平倉與 `last_exit_at`，不重新解讀舊 EF 訊號、不新增冷卻、不補單。只有升級後接收到的新 EF 訊號套用新進場規則。

## 不加 H3

- 服務不讀取 H3 訊號、價格或浮盈虧，也不使用游擊方向或數值門檻。
- 保留 13 個 EF 追蹤方向、反向否決、原始 `-1→0` 追蹤為多、原始 `1→0` 當筆多單出場、22:00 進場截止、15 分鐘冷卻與 01:00 清倉。
- 狀態記錄 `h3_entry_policy=disabled`、`broker_simulation=true`。升級保留既有部位與冷卻，重啟不補舊單。

## -1→0 轉多

- 收到任一子策略 CSV 原始 `previous_position=-1、new_position=0`，將該策略的 JSON **追蹤方向**設為 `+1`，直到該策略下一筆訊號或每日重設。
- 判斷用原始轉換，不用當天 JSON 的舊方向。當日歸零後第一筆原始 `-1→0` 仍可設為 `+1`。
- 其餘訊號將追蹤方向更新為原始 `new_position`。`1→0` 仍追蹤為 `0`，並保留原有的當筆多單目標歸零規則。
- 合併 13 個追蹤方向後仍套用反向否決、Clamp、U 倍數、22:00 截止與 15 分鐘冷卻。`-1→0` 不保證開多：若其他策略仍追蹤 `-1`，帳戶目標為 `0`；它建立的 `+1` 同樣否決空單。
- 被截止或冷卻擋住也保存 `+1`，到期不自動下單，等待下一筆新訊號再計算。
- 原始訊號保留在 `source.signal_previous_position` / `source.new_position`，有效方向存於 `source.tracked_position` 與最外層 `positions`。通知會明列「原始-1→0，追蹤方向改為+1」。

## 新進場限制

- 以 CSV `received_at`（台灣時間）判斷，只接受 08:45（含）至 22:00（不含）的新進場訊號。21:59:40 收到、22:00 才處理的訊號仍可進場；午夜不重新開放。
- 22:00 不強制平倉。已有同方向部位可維持或減倉，原 Clamp 出場條件及翌日 01:00 清倉照常執行；22:00 後不能增加持倉或開反向倉，被擋的反手只平掉原倉。
- 不論盈虧，實際平掉舊方向部位後，多空共用冷卻 15 分鐘。以券商成交明細中完成平倉的時間起算，部分平倉不算完成；委託送出或 API 返回不代表成交。
- 平倉未確認時暫停新進場，出場仍可執行。最多每 5 秒唯讀查詢平倉委託及庫存，不重送前筆委託。若沒有成交時間，但確認舊方向已清除且沒有未結 TMF 委託，保守以庫存確認時間起算。
- 例如 19:20:08 平倉，19:35:08 起收到的新訊號才可再進場；21:45 平倉則因 22:00 截止，當晚不再新進場。冷卻到期本身不會下單，也不補送冷卻中被擋的訊號。
- 沿用研究版本的原子反手：同一訊號直接多轉空／空轉多，若截止及前次冷卻均允許，可一次反手；這次舊方向的平倉成交會啟動後續冷卻，不額外改成「先平倉再等 15 分鐘才反手」。
- 被擋的訊號仍更新 13 個子策略 JSON 部位與處理進度；每筆新訊號以券商實際庫存判斷是否真的新增曝險，不能因 JSON 還指向多單就在截止後重新開多。
- `runtime/live_state.json` 的 `entry_policy` 保存上次平倉時間、時間依據、待確認平倉與庫存觀察；重啟、午休、15:00、午夜均保留。沿用既有每日重設流程，確認空手後才清除上一週期的冷卻狀態；清倉未確認則保留待核對資訊。
- 首次升級缺少進場限制紀錄的舊狀態時，嘗試恢復最後一筆待確認平倉。舊狀態沒有可用成交紀錄且當下空手時，從第一次確認空手起保守冷卻 15 分鐘；之後重啟不重複起算。已有 schema 9 的 60 分鐘版保留原紀錄；新安裝空白狀態不加這個遷移冷卻。

多空對稱出場規則：只要目前任一子策略部位是 `-1`，就否決多單；
只要目前任一子策略部位是 `+1`，就否決空單。這包含 `1→-1` 與
`-1→+1` 的直接反轉。即使 13 策略合計方向相反，券商目標也為空手。
反向策略離開該部位後，若合計仍指向原帳戶方向，且截止與冷卻均允許，收到新訊號後才可重新進場。
額外的多單出場規則：收到任一子策略的原始 `previous_position=1、new_position=0`，若本筆 Clamp 方向原為多，將本筆目標歸零。判斷使用 CSV 原始轉換，即使該策略在 JSON 追蹤為 0 也適用；券商有多單即送出平多目標，空手時不因其他策略仍為 +1 而開多。原始 `-1→0` 則按上述規則將該策略追蹤為 `+1`，不另加一次性強制出場規則。

例如 A、B、C 追蹤為 +1，D 追蹤為 0，帳戶持多一口：D 傳來原始 `1→0` 時平多，A、B、C 的 +1 保留。本條只作用於當筆事件，不累積次數、不鎖死整天；實際平倉確認後冷卻 15 分鐘，之後的新訊號可依保留的追蹤部位、否決者與進場時間限制重新進場。冷卻到期本身不補單。
每日重設清除兩種否決者；昨天的部位不帶到今天。

## 每日流程

- 13 個子策略的唯一追蹤方向來源是 `runtime/live_state.json` 的 `positions`。每個值只能是 -1、0、1；這是 Clamp 的有效方向，不等於上游策略的實際倉位。CSV 只提供新訊號及歷史查核，不回放覆蓋 JSON。`long_veto_strategies` 記錄所有追蹤為 `-1` 的策略；`short_veto_strategies` 記錄所有追蹤為 `+1` 的策略，兩者在啟動與每筆訊號後由 `positions` 重建。
- 台北時間 08:45～13:45、15:00～隔天 05:00 為同一交易日；午休、15:00、午夜與程式重啟都不歸零。
- 01:00 查永豐 2 TMF 庫存並送一次清倉委託，保留 JSON 部位至確認空手。01:00 起停止新訊號交易。
- 01:00 清倉失敗或結果不明，Discord 明確通知人工核對及清倉，不自動重送。
- 05:05 查詢庫存及未結委託，確認 TMF 空手即將 13 個策略部位歸零。未確認則通知人工處理，開盤前最多每分鐘重查一次。到日曆規定的重新開盤時間（一般08:45），即使仍未確認空手，也將策略 JSON 歸零並處理新訊號；保留 `manual_flat_required`，不宣稱券商已空手，不因清倉失敗鎖定新單，也不再重設已開始的新時段部位。
- 停機錯過 05:05，啟動後補做檢查。成功重設記錄 `last_reset_cycle`，同一周期不重設第二次。週末及休市依 config/calendar.json 處理。
- 收到新訊號後，先更新該策略的 JSON 追蹤方向（原始 `-1→0` 設為 `+1`，其餘設為 `new_position`），計算全部策略的最終目標口數，再查永豐 2 當下 TMF 實際庫存。本次委託固定為 `最終目標口數 - 券商目前庫存`。
- 13 策略 JSON 保留完整合計淨方向。淨方向大於 0 且沒有空方否決者時原始目標為 `+U`，有空方否決者時為 0；淨方向小於 0 且沒有多方否決者時原始目標為 `-U`，有多方否決者時為 0；等於 0 時空手。每筆訊號先更新 JSON，再查永豐 2 當下 TMF 實際庫存，套用截止與冷卻後送出與最終目標的差額；U 由 `EF_MORNING_WEEKEND_HEDGE_UNIT` 設定。即使原始淨方向超過 ±1，也不會因超限而跳過下單。01:00 清倉仍固定以 0 為目標。
- 原始 `1→0` 事件在套用截止與冷卻前，先將當筆正方向目標改為 0；不清除其他策略的 JSON 部位。U 倍數設定不變。
- 啟動前、停機期間與等待重設期間已收到的訊號不補單。

| +2 | +1 | 賣出1口 |

## 重啟與送單狀態

每筆新 EF 訊號都先更新並計算 JSON 淨方向與兩種否決者，再決定 -1/0/+1 目標，乘上 `EF_MORNING_WEEKEND_HEDGE_UNIT` 後查券商 TMF 庫存、計算差額並送出一筆 IOC 委託。不掃描、不等待前一筆委託狀態，也不因中斷記錄鎖定新訊號。更新部位、否決者與訊號進度會在券商操作前一起保存。

送單前將 positions、新訊號進度、目前庫存、最終口數與預計委託一起保存。一般委託只送一次，不重試；平倉成交會唯讀查詢，以正確起算冷卻。如果程式在送單途中中斷，該筆標記為 `interrupted_no_retry`，待確認平倉保留，後續新訊號仍以當下券商庫存及進場限制重新計算。

首次升級 v4 時，從既有 `day_signal_positions` 快照遷移一次到 `positions`，保留當日部位，不回放 CSV。遷移後刪除 `day_signal_positions`；每次存檔也移除 `source.positions`、`source.net_position`，避免保存重複且可能過期的部位快照。`source.last_signal` 與該筆訊號明細仍保留作為處理進度；手動修改策略部位時使用最外層 `positions`，啟動時會據此重建兩種否決清單。

升級舊版狀態時，不論舊否決清單內容為何，都由目前 `positions` 重建；直接反轉而仍持倉的策略也會成為否決者。服務重啟本身不會補送舊訊號或立即重算委託，仍須等新訊號。

## 手動修改

1. 停止 `ef-morning-weekend-hedge-strategy` 服務。
2. 備份 `runtime/live_state.json`，核對券商實際部位及委託紀錄。
3. 調整 `positions` 中對應策略的 -1 / 0 / 1，必須保留全部13個策略。重新啟動時會從 `positions` 重建 `long_veto_strategies` 與 `short_veto_strategies`。
4. 啟動服務，JSON 會直接沿用；修改檔案本身不會觸發補單。

請勿在服務運行中改檔，程式不會即時重新載入，並可能覆寫人工修改。

## 帳戶通知

入口目前使用 API_KEY2 Shioaji 模擬帳戶（`simulation=True`）。Discord 通知策略開始、訊號委託及 01:00 清倉。每筆訊號通知區分子策略的進出場訊號、套用進場限制後的帳戶目標、券商目前庫存與本次預計下單，並顯示被截止或冷卻擋下的原因。若未取得券商庫存或委託計畫，預計下單顯示「尚未確認」，不顯示「無需下單」。送單失敗或結果不明時，通知人工核對帳戶委託及庫存；委託已送出不表示已成交。

平倉成交的 `status.deals[].ts` 與 `update_status` 用法依 [Shioaji 委託狀態文件](https://sinotrade.github.io/tutor/order/UpdateStatus/)。
